# Agent Note: self-update resets onto upstream and overlays its own tree, instead of merging

Status: implemented

## Problem

The self-update job's original design (see [the web sidebar self-update button note](../feature/2026-08-29-web-self-update-button.md)) merged the fetched upstream branch into the checkout's own branch with `git merge --no-edit`, so the checkout's history carried this feature's own commits (and any other fork-local history) diverged from upstream. The first real deployment against a fork that had drifted hundreds of commits behind upstream produced exactly the conflict this risked: `knip.json` (deleted upstream, present locally), `packages/experimental/README.md`, and `pnpm-lock.yaml` all conflicted, because upstream's own releases had independently touched files this deployment's local commits also touched. This was not a one-off — every upstream release that touches one of those shared files reproduces the same conflict, since the checkout's own history never stops diverging from upstream's.

Separately, the active-Sessions acknowledgement gate (`start` refusing with `active-sessions-need-acknowledgement` until the caller set `acknowledgeActiveSessions: true`, with the panel showing a confirmation step and a warning) added a second obstacle an operator had to clear on every update, for a risk (an interrupted in-flight turn) the harness already repairs transparently on next open regardless of whether the caller acknowledged it. The operator explicitly asked to remove both obstacles: no merge conflicts, ever, and no confirmation step of any kind.

## Decision

The checkout's own branch is now a pristine mirror of `upstream/branch`, never diverged from by an ordinary commit. Everything this deployment adds on top of upstream (the three self-update packages themselves, and any other deployment-local plugin) lives in a separate, dedicated git ref (`overlayRef`, a local branch — `self-update-plugin` in this deployment) whose tree is restored onto the mirrored checkout after every reset, then committed as exactly one commit. The job's phases changed from `preflight → fetching → backing-up → merging → installing → building → verifying → restarting` to `preflight → fetching → backing-up → resetting → overlaying → installing → building → verifying → committing → restarting`:

- `resetting` runs `git reset --hard <fetched upstream head>` — never a merge. Upstream's own history is never diverged into, so there is nothing for a future upstream commit to conflict with; this eliminates the conflict class entirely rather than handling it more gracefully.
- `overlaying` runs `git checkout <overlayRef> -- <overlayPaths...>` (`SelfUpdateGit.restorePaths`), restoring exactly the configured paths from `overlayRef`'s tree onto the just-reset working tree and index. A path listed in `overlayPaths` but missing from `overlayRef`'s tree fails this step (`overlay-failed`) rather than silently omitting it. `overlayRef` not existing at all fails `preflight` (`overlay-ref-missing`) before anything mutates.
- `committing` (after install/build/verify all succeed) runs `git add -A` then `git commit --no-verify -m 'self-update: overlay <overlayRef> onto <sha>'` (`SelfUpdateGit.commitAll`) — hooks are bypassed because the overlay's paths are already-reviewed source restored verbatim from `overlayRef`, not new work a hook needs to gate. This is the only commit this package ever creates, and it is exactly what the next update's `resetHard` discards; the checkout's history stays a straight line of upstream commits, each followed immediately by at most one overlay commit that never survives the next update.
- Rollback (on install/build/verify/commit failure) is unchanged in mechanism — `git reset --hard <preUpdateHead>` plus a fresh install and build — but now also covers a failed `committing` (`commit-failed` joins `install-failed`/`build-failed` as a rollback trigger).

`SelfUpdateGit.merge` is deleted, along with the failure codes it produced (`merge-conflict`, `merge-failed`, `merge-unrecoverable` — the last renamed to a general-purpose `unexpected` fallback still used by `toFailure`'s last-resort branch for a genuinely unwrapped bug). New failure codes: `overlay-ref-missing`, `reset-failed`, `overlay-failed`, `commit-failed`. `Config` gains two required fields: `overlayRef` (the ref name) and `overlayPaths` (the paths restored from it).

`start` no longer takes a request object, refuses on active Sessions, or reports `active-sessions-need-acknowledgement`. Every Session currently attached to a live fiber is flushed unconditionally before a job starts, exactly as before, but with no gate and no caller-supplied acknowledgement — an in-flight turn is interrupted and transparently repaired on next open regardless, so asking added friction without changing the outcome. `SelfUpdateStatusValue` drops `activeSessions` (no longer read by anything). The browser panel drops its confirmation step, "Update anyway" button, and active-Sessions warning entirely: one "Update" click starts a job immediately. The panel also now stays open and ignores an outside click or Escape while a job is active, and opens on its own the instant a job becomes active (including one started from another tab or a stale retried click), so a running job's live phase and log can never be lost behind an accidental close.

Because the checkout's own registrations for these three packages (root `tsconfig.host.json`/`tsconfig.client.json` project references, `knip.json` entries, the `scripts/run-gates.ts` built-lib-smoke file list, and the `packages/experimental/README.md` table row) are themselves files upstream does not know about, they are deliberately *not* part of `overlayPaths` — restoring them every update would immediately reintroduce the conflict class this design exists to remove, since upstream's own future edits to those same shared files would then collide with the overlay's copies on every subsequent reset. Instead, `overlayRef`'s own tree carries a small `overlay/build.mjs` script (referenced directly as `buildArgv`) that `tsc -b`s the three overlay packages' own `tsconfig.json` files before invoking the ordinary root `pnpm run build` — the root aggregates a pristine `upstream/branch` never lists these packages, so their own build step must run standalone, outside those aggregates, every time. The root registrations continue to exist only in a separate development branch/worktree based on `overlayRef`, where a maintainer edits and typechecks the overlay's own source with full project-reference support; that branch is never merged into (or reset from) the deployment's own tracked branch.

## Alternatives considered

**Keeping `git merge` but resolving conflicts automatically** (`-X theirs`, or auto-favoring one side per path) was rejected: silently discarding either side's changes on a real conflict is exactly the kind of surprising, hard-to-audit behavior an unattended update must not risk, and it does not remove the conflict class — it only hides each occurrence's effect, which could just as easily discard something the operator needed.

**Rebasing the checkout's own commits onto the fetched upstream tip** was rejected for the same reason merges were originally rejected in favor of `--no-edit`: it rewrites commit history and requires a force-push (or, for a purely local checkout, still leaves the same one-git-history-diverging-from-upstream shape that produces conflicts on the next rebase). Resetting and overlaying keeps the checkout's history a strict linear mirror of upstream with no rewriting.

**Keeping the active-Sessions acknowledgement gate but making it non-blocking (informational only)** was considered and rejected in favor of removing it entirely: an informational warning the operator must still read and click past is still an obstacle for a risk the harness already repairs transparently regardless of acknowledgement; removing the gate outright matches the explicit ask ("делай обновление форсированно... я не хочу видеть этих проблем") without losing any actual safety, since nothing about the repair path depended on the caller having acknowledged anything.

**Deriving `overlayPaths` automatically from `overlayRef`'s diff against some common ancestor** was considered and rejected: it would need a stable base commit to diff against, which does not exist once the checkout's own history is reset every update (the "ancestor" a diff would use keeps moving); an explicit, maintainer-edited path list is simpler and its one failure mode (a forgotten path) is a loud `overlay-failed`-adjacent oversight the maintainer discovers immediately in the panel's log, not a silent one.

## Consequences

An update against a fork arbitrarily far behind upstream can never conflict, because the checkout's own history never diverges from upstream in the first place — the entire conflict class the original merge-based design carried is gone, not merely handled better. The cost is a small, permanent maintenance burden: `overlayPaths` is a hand-maintained allowlist (see the `self-update` and `self-update-web-profile` READMEs' Known Limitations), and the overlay's own packages must build standalone via `overlay/build.mjs` rather than through the ordinary root project-reference aggregates, since those aggregates intentionally never list packages upstream does not know about. Developing the overlay itself now requires a separate branch or worktree carrying the root registrations that never ship to the deployment's own tracked branch — a real (if small) departure from editing everything in one checkout.

Removing the active-Sessions gate means an operator can no longer choose to wait for in-flight turns to finish before updating; every update now unconditionally interrupts them, relying entirely on the harness's crash-recovery repair. This was an explicit, informed trade the operator asked for, not a default this package would pick for an unattended or multi-operator deployment on its own.
