# Agent Note: Web sidebar self-update button

Status: implemented

## Problem

A source-checkout `dsh web` deployment on a fork tracks an `upstream` remote by hand: pulling, merging, reinstalling, rebuilding, and restarting all require a terminal and enough context to recover safely from a failed merge or a broken build. A single-operator deployment supervised by a process manager (pm2, systemd, launchd) has no way to trigger or observe that sequence from the browser it already lives in, and every step risks leaving the checkout in a state that will not boot — with no guarantee that in-progress conversations survive.

## Decision

Three private `packages/experimental/*` packages implement a browser-triggered update: `self-update` (Host Remote service), `client-ui-self-update` (browser sidebar button and panel), and `self-update-web-profile` (the bundle patch that mounts both into a `web` profile).

`SelfUpdateService` (`ctx.selfUpdate`, namespace `selfUpdate`) exposes `status`, `check`, `start`, and a `follow` stream. `start` creates at most one `SelfUpdateJob` at a time — a single lifecycle controller with a frozen, replaced-not-mutated snapshot — and refuses synchronously (no job created) when another job is running, the working tree is dirty, no bounded exit request (`ctx.get('appExit')`) is available, or one or more Sessions are currently attached to a live fiber and the caller has not set `acknowledgeActiveSessions: true`.

A job runs `preflight → fetching → backing-up → merging → installing → building → verifying → restarting`. `fetching` reads `git rev-list --left-right --count HEAD...<remote>/<branch>` against the configured remote and branch; `behind === 0` ends the job with outcome `up-to-date` before anything mutates. `merging` runs `git merge --no-edit <remote>/<branch>`; on a non-zero exit it checks whether `MERGE_HEAD` exists before deciding how to report it, rather than assuming every non-zero exit is a real conflict. A fast-forward-eligible merge never writes `MERGE_HEAD`, so a transient `git merge` failure there (no conflict, working tree unchanged) is reported as `merge-failed` without ever invoking `--abort`; only a real conflicted merge (`MERGE_HEAD` present) is aborted and reported as `merge-conflict`. Either way the repository is never left conflicted. (This was found, not designed up front: an early version always ran `--abort` on any non-zero exit; under parallel test-suite load, a fast-forward merge occasionally failed transiently, and the unconditional `--abort` then itself failed with "no merge to abort," misreporting a harmless, retriable failure as `merge-unrecoverable`. `git status` at the moment of failure confirmed the tree was clean and merely behind — proving the bug was in this classification, not in git or in concurrent test execution.) `installing`/`building`/`verifying` run deployment-configured argv (`installArgv`, `buildArgv`, `verifyArgv`) through one shared streaming runner built on `ctx.subprocess`, decoding stdout/stderr into log lines forwarded live to every open `follow` subscriber. A failure in any of those three phases triggers an automated rollback: `git reset --hard <preUpdateHead>` (safe because preflight already required a clean tree at that exact commit) followed by a fresh install and build against the reverted commit, so the still-running old process's on-disk artifacts never drift from its own git tree. A rollback whose own install/build also fails reports the distinct `rollback-failed` code rather than being folded into an ordinary build failure. On success, `restarting` publishes a final `done` frame to every stream, then calls `appExit(0)` on the next microtask; the service never restarts the process itself, and relies entirely on the external supervisor's restart-on-clean-exit policy.

Every deployment-varying value (`repoRoot`, `remoteName`, `branch`, `installArgv`, `buildArgv`, `verifyArgv`, `extraPathDirs`, `backupRoot`, `keepBackups`, `sessionsDir`, `storagesDir`, `attachmentsDir`, `graceMs`, `maxLogLines`) is a required `Config` field with no default; `extraPathDirs` closes the gap between a process supervisor's minimal `PATH` and wherever the deployment's package manager actually lives.

Session data is never in the automated rollback's scope: `~/.dsh/sessions`, `~/.dsh/storages`, and `~/.dsh/attachments` live entirely outside the git checkout, so no phase of this job (`merge`, install, build, verify, or their rollback) can touch them. `backing-up` still copies those three directories into a timestamped `backupRoot` subdirectory with a manifest naming the pre-update commit, purely as a disaster-recovery artifact for a human operator, and prunes snapshots beyond `keepBackups`. A Session interrupted mid-turn by the eventual restart is repaired transparently on its next open by the harness's own crash-recovery path (`interruptedTurnClosers`), which the `acknowledgeActiveSessions` gate exists to make an informed choice rather than a silent one.

The browser half mounts the generated Remote contribution via `ctx.remote.$mount` (the package is not a built-in `dsh-api-remotes` member) and registers one entry into the stable `sidebar.footer.action` slot. `SelfUpdateController`, a plain browser-local object layer, opens exactly one `follow` subscription per panel lifetime and always seeds from that stream's baseline frame, so a late subscriber, a second browser tab, or a component remounted by dev-mode client HMR (which stat-polls and hot-swaps client bundles independently of this job) all start from the complete current state. `onReconnect` exposes the physical `connection/reset` event as a callback registration rather than a raw `ctx` read, per the client package's ctx-discipline rule; the panel calls `window.location.reload()` once a reconnect arrives while it believes a restart is in progress, guaranteeing every client bundle is fresh after the swap.

## Alternatives considered

**A dedicated `SESSION_FORMAT_VERSION` preflight check** (diffing the constant's source text between the local and fetched-upstream `packages/core/session/src/types.ts`) was rejected: the harness's own session-persistence coordinator already refuses an incompatible format on read, fail-closed, with a directional diagnostic — a second preflight check would only duplicate an already-safe mechanism against a brittle blob-diff of a file whose location and shape are not part of any public contract.

**Restarting via `appExit(0)` immediately after `buildArgv` exits 0, with no separate verification step** was rejected in favor of an explicit `verifying` phase: a build that produces a boot-crashing artifact would otherwise crash-loop the new process indefinitely under the supervisor's own restart policy, with no signal back to the browser. `verifyArgv` (a `--dump-config` invocation against the freshly built launcher) is a cheap, bounded smoke test that still cannot fully prove the next real boot succeeds — a residual risk the package's README states rather than papering over.

**A pre-update backup step feeding the automated rollback path** was rejected in favor of keeping backup and rollback fully independent: Session data lives outside the git checkout, so no operation this feature performs can corrupt it, and restoring `~/.dsh/sessions` from a backup after a partial write risks losing or duplicating events the automated path never needed to touch. The backup exists solely for a human, triggered before any repository mutation.

**Hardcoding the package manager's absolute path in `Config`** was rejected in favor of the harness's own `ctx.subprocess.resolveExecutable` seam plus a configurable `extraPathDirs`: this keeps the package portable across any process-supervisor PATH, rather than baking one machine's layout into source.

**Merging with `git merge --no-edit` (preserving the fork's own local commits, including this feature's own) rather than a fast-forward-only merge or a rebase** was the explicit choice for a fork with pre-existing local history: `--ff-only` would fail outright once local commits exist, and a rebase would rewrite and force-push those commits, which the update flow does not perform.

## Consequences

An operator triggers, watches, and recovers from an upstream update entirely from the browser, with the running process never left serving artifacts that do not match its own git tree even when the update fails partway through. The design buys this safety by doing nothing to reduce the two residual risks named in the package's own Known Limitations: a `verifyArgv` pass that still crash-loops on real boot needs the supervisor's own restart-count ceiling and manual recovery, and a rollback whose own rebuild also fails needs a human at a terminal. No cross-process lock exists against a manually invoked `pnpm install` racing a job's own install phase.
